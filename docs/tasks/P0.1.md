# P0.1 — cgo + NSPanel spike

**Branch:** feat/P0.1   **Phase:** 0   **Depends on:** none   **Blocks:** P3.1, P3.2

## Goal

Show a borderless panel from Go and find out what "summon → pixels on screen" actually costs. This is
the budget that matters most (< 100 ms) and the one the whole product feel rests on. P3.1 is designed
against whatever this finds.

## Files you may touch

- `spike/panel/` (new)
- `docs/DECISIONS.md` (append)
- `docs/ROADMAP.md` (box + log)

## What has to be answered

1. Can a borderless, non-activating panel be created and shown from a Go process that is not a bundled
   `.app`, and does it appear above full-screen apps and on every Space?
2. **What does summon → pixels cost, cold and warm?** Cold includes NSApp and window creation; warm is
   the only number the user ever feels, because the real panel is created once and re-shown.
3. Is `orderFront` returning the same thing as pixels being on screen? ALTTAB-LESSONS says CoreAnimation
   commits at the end of the runloop turn, so it should not be — measure the gap rather than assume it.
4. Does showing the panel steal focus from the app the user is switching away from?

## Acceptance

- [x] A borderless panel with drawn content appears on screen, from Go — verified by screenshot, not
      only by the absence of an error
- [x] summon → pixels measured cold and warm — **1.3 ms warm, 14 ms cold**, ~1% of budget. "On screen"
      is defined as the `CATransaction` completion block firing, i.e. the frame handed to the render
      server; photons are up to one display refresh later, and D13 says so rather than eliding it
- [x] The gap is quantified: the call returns in ~1 ms while the cold frame commits at ~14 ms — measuring
      the call would have been wrong by an order of magnitude
- [x] Findings appended to `docs/DECISIONS.md` (D13)
- [x] Bonus, because it would have invalidated the warm number: `drawRect:` instrumented to prove all 30
      warm summons genuinely re-render rather than being served from a cached backing store
- [ ] **Open, needs a human:** over a full-screen app, and across Spaces. `collectionBehavior` is set
      from AltTab's prior art but neither behaviour was tested — TCC blocks driving it synthetically

## Notes

The panel is drawn as **one view** with all tiles in it, not one view per tile — that is P3.1's design
(AltTab has 53 `NSView` subclasses and pays for it), and measuring a single empty window instead would
flatter the number for a shape we are not going to build.

Do not measure `makeKeyAndOrderFront` returning and call it summon latency. Use a `CATransaction`
completion block and the following main-queue turn, and report all three numbers so the difference is
visible rather than assumed.

TCC judges the *responsible* process, not the binary (ALTTAB-LESSONS §5) — irrelevant here since a panel
needs no permission, but it is why this spike must not grow a window-list dependency.
