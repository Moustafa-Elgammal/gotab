# V6.12 — Release automation (CI/CD)

**Branch:** ci/release-workflow   **Phase:** 6   **Depends on:** P4.5 (`build.sh` produces a signed
universal `.app`), P5.3 (`internal/update` reads `FeedURL`)

## Goal

A `v*` tag push is the whole release process. GitHub Actions runs the gate, builds `GoTab.app` with
the tag as its marketing version, cuts a GitHub Release carrying the zipped bundle and its SHA-256,
and (re)publishes `latest.json` to GitHub Pages — which is what `internal/update.FeedURL` now points
at. This is the infrastructure half of V6.11: it gives that check a real host to run against.

Scope is check-only, exactly as D39 draws it. **Not** in this task: notarization / Developer ID
signing, and in-app download / verify / relaunch of an update. Both are gated on an Apple Developer
account and are separate future work.

## Manual prerequisites (done in the GitHub UI, once the repo is public)

1. **Settings → Pages → Build and deployment → Source → "GitHub Actions".** Until this is set the
   `deploy-pages` job fails; the Release is still cut.
2. **Settings → Actions → General → Workflow permissions** must not be locked down in a way that
   overrides the per-job `permissions:` blocks (the defaults are fine).
3. **Settings → Environments → `github-pages` → Deployment branches and tags** — the auto-created
   environment allows only the default branch, so a *tag*-triggered deploy is rejected with
   "Tag 'vX.Y.Z' is not allowed to deploy to github-pages due to environment protection rules".
   Add a rule of **Ref type: Tag, pattern `v*`** (or set "No restriction"). Found on the first run;
   see Findings.
4. Pages on a private repo needs a paid plan; the plan is to publish the repo, so this is a
   non-issue — just a note on why nothing serves before then.

## Notes

- `deploy-pages` and `release` are separate jobs on purpose: a first tag pushed before the Pages
  setting is flipped still produces a usable Release, and the Pages step just needs re-running.
- The zip is ad-hoc signed. A downloader on another machine gets a Gatekeeper prompt and needs
  right-click → Open (or `xattr -dr com.apple.quarantine`). A notarization step in the workflow is
  the fix and is a follow-up task, not part of this one.
- `BUNDLE_ID` stays `app.gotab`. Renaming it now would orphan the CFPreferences domain and the TCC
  grants (D34) — a deliberate non-goal here.

## Findings

_2026-09-08 — first end-to-end run, tag `v0.2.0` (commit `ed23786`)._

**The `release` job worked first try.** Gate → `build.sh` (universal, ad-hoc signed) → `ditto` zip →
`shasum` → `gh release create` → render `_site/latest.json` → `upload-pages-artifact`, all green.
The Release carries `GoTab-v0.2.0.zip` + `.sha256`; the downloaded zip's SHA-256 matches the
published sum, the bundle's `CFBundleShortVersionString` is `0.2.0`, and `codesign --verify --strict`
passes. So the build/sign/package/publish half of D42 holds as written.

**`deploy-pages` failed twice before going green — both times a repo *setting*, not the workflow:**

1. **Pages not enabled.** Fixed by Settings → Pages → Source → "GitHub Actions" (prereq 1).
2. **Environment protection rule.** The auto-created `github-pages` environment only allowed the
   default branch, so the tag-triggered deploy was rejected outright: *"Tag 'v0.2.0' is not allowed
   to deploy to github-pages due to environment protection rules."* Fixed by adding a **Ref type:
   Tag, pattern `v*`** rule (Settings → Environments → `github-pages`). Now recorded as prereq 3.
   Re-running the failed job (the `release` job's artifact is retained) then published cleanly —
   no re-tag needed.

**The feed serves, with a redirect.** `https://moustafa-elgammal.github.io/gotab/latest.json`
`301`s to `https://elgx.me/gotab/latest.json` (a custom domain on the account's Pages). The rendered
manifest is correct: `version` `0.2.0`, `url` the release tag page, `min_macos` `12.0`. `FeedURL`
stays on the `github.io` URL deliberately — v0.2.0 already ships it, Go follows the redirect, and it
keeps working if the custom domain is ever dropped.

**Bug found and fixed here: `notes` was the commit subject, not the tag message.** `actions/checkout`
writes a lightweight ref at the tag name (pointing at the commit), which shadows the annotated tag
object, so `git tag -l --format='%(contents:subject)'` returned `ed23786`'s subject
("chore: automate releases, …") instead of the `v0.2.0` message. Fix in the same commit as this
note: `git fetch --force origin "refs/tags/<tag>:refs/tags/<tag>"` in the "Derive version and notes"
step before reading the subject. The already-published v0.2.0 Release body / manifest `notes` still
carry the commit subject; harmless, and a re-render would need another Pages deploy.

**`gotab -check-update` against the live URL is still unrun — that is V6.11.** V6.12's job was to
give it a host; that host now exists and answers.
