# V6.12 — Release automation (CI/CD)

**Branch:** ci/release-workflow   **Phase:** 6   **Depends on:** P4.5 (`build.sh` produces a signed
universal `.app`), P5.3 (`internal/update` reads `FeedURL`)

## Goal

A `v*` tag push is the whole release process. GitHub Actions runs the gate, builds `GoTab.app` with
the tag as its marketing version, cuts a GitHub Release carrying the zipped bundle and its SHA-256,
and (re)publishes `latest.json` to GitHub Pages — which is what `internal/update.FeedURL` now points
at. This is the infrastructure half of V6.11: it gives that check a real host to run against.

Scope is check-only, exactly as D39 draws it. **Not** in this task: notarization / Developer ID
signing, and in-app download / verify / relaunch of an update. Both are gated on an Apple Developer
account and are separate future work.

## Manual prerequisites (done in the GitHub UI, once the repo is public)

1. **Settings → Pages → Build and deployment → Source → "GitHub Actions".** Until this is set the
   `deploy-pages` job fails; the Release is still cut.
2. **Settings → Actions → General → Workflow permissions** must not be locked down in a way that
   overrides the per-job `permissions:` blocks (the defaults are fine).
3. Pages on a private repo needs a paid plan; the plan is to publish the repo, so this is a
   non-issue — just a note on why nothing serves before then.

## Notes

- `deploy-pages` and `release` are separate jobs on purpose: a first tag pushed before the Pages
  setting is flipped still produces a usable Release, and the Pages step just needs re-running.
- The zip is ad-hoc signed. A downloader on another machine gets a Gatekeeper prompt and needs
  right-click → Open (or `xattr -dr com.apple.quarantine`). A notarization step in the workflow is
  the fix and is a follow-up task, not part of this one.
- `BUNDLE_ID` stays `app.gotab`. Renaming it now would orphan the CFPreferences domain and the TCC
  grants (D34) — a deliberate non-goal here.
