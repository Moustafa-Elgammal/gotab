# P3.4 — Theme / appearance / dark mode

**Branch:** feat/P3.4  **Phase:** 3  **Depends on:** P3.1 (palette + material setters)
**Owns:** `internal/platform/darwin/theme.h`, `theme.m`, `theme.go`

## Goal

Decide the panel's colours and vibrancy from the system's **effective appearance**, apply them through
the two frozen setters P3.1 exposes (`gt_panel_set_palette`, `gt_panel_set_material`), and keep them
in step when the user switches Light/Dark mid-session. The panel should look native in both, and never
flash an unstyled frame.

- `docs/tasks/P3.4.md` (this file)

**Do not touch** `panel.*` (P3.1 — call its frozen accessors/setters, add nothing to it), `shim.*`,

`docs/DECISIONS.md`.

## Contract

Expose (final names yours, this shape):

```go
// ApplyTheme reads the current effective appearance and pushes a palette + material to the panel.
// Safe to call before or after CreatePanel; a call before is remembered and replayed.
func ApplyTheme() error

// WatchAppearance calls onChange (which should call ApplyTheme) whenever the effective appearance
// flips. onChange runs on the main thread and must return immediately. StopWatchingAppearance ends it.
func WatchAppearance(onChange func()) error
func StopWatchingAppearance()
```

- Read the effective appearance from `NSApp.effectiveAppearance` (or the panel's, via
  `gt_panel_effect_view()`), matched against `NSAppearanceNameDarkAqua` — not `AppleInterfaceStyle`
  from user defaults, which misses the per-app override and the auto Light/Dark schedule.
- Build the `gt_palette` for each appearance. The colour *choices* may live on the Go side of this
  task; the reading and the KVO/notification observing are ObjC in `theme.m`.
- Pick the `NSVisualEffectMaterial` (a `HUD`-ish material reads right for a floating switcher). Pass
  `GT_MATERIAL_NONE` to fall back to `palette.panel_bg` if you decide vibrancy is wrong here.
- The appearance observer callback does nothing but call `onChange` — same rule as P2.3b's observers
  (`ARCHITECTURE.md#the-cgo-rule`).
- No leaked observer / KVO registration on `StopWatchingAppearance`.

## Findings (P3.4)

**Files added:** `internal/platform/darwin/theme.h`, `theme.m`, `theme.go`. Nothing else touched.
`panel.*` / `shim.*` unmodified.

**Shape delivered.** `ApplyTheme() error`, `WatchAppearance(onChange func()) error` +
`StopWatchingAppearance()`, plus `ErrNilThemeCallback`. `theme.m` exports `gt_theme_is_dark`,
`gt_theme_material`, `gt_theme_watch_start`, `gt_theme_watch_stop`; `theme.go` exports `goThemeChanged`
for the KVO hand-off.

**Appearance reading.** `gt_theme_is_dark` reads the panel's `NSVisualEffectView.effectiveAppearance`
once the panel exists (that carries any per-window override), else `NSApp.effectiveAppearance`, and
resolves it with `-bestMatchFromAppearancesWithNames:@[Aqua, DarkAqua]` — so the a11y high-contrast
appearances fold onto the right side, and the per-app override + auto schedule that
`AppleInterfaceStyle` misses are both honoured. Confirmed tracking a forced `NSApp.appearance` in both
directions, pre- and post-`CreatePanel`.

**Material.** `NSVisualEffectMaterialHUDWindow`, resolved by name in `theme.m` so no magic number sits
in Go. Vibrancy kept on (not `GT_MATERIAL_NONE`): a HUD blur is the native look for a floating
switcher, and the palette's `tile_bg` values are deliberately light washes that assume the blur is
behind them. `panel_bg` is set in both palettes purely as the `GT_MATERIAL_NONE` fallback.

**Watcher.** KVO on `NSApp.effectiveAppearance`, not the `AppleInterfaceThemeChangedNotification`
distributed notification — the latter is the `NSUserDefaults` mechanism, fires only for the system
setting, and misses a per-app override. The callback does nothing but call `goThemeChanged()`
(cgo rule). `goThemeChanged` loads an `atomic.Pointer[func()]` and calls it — identical shape to
`observe.go`'s `goObserveChange`. Fired exactly on real flips, never on a no-op set, never after
`StopWatchingAppearance`.

**ApplyTheme-before-create: integrator help IS needed.** A pre-`CreatePanel` `ApplyTheme` cannot be
replayed from `theme.go` — there is no create hook to hang a replay on, and `theme.*` may not add one
to `panel.*`. Worse, the skeleton `gt_panel_set_material` early-returns when `g_effect == nil`, and
`gt_panel_create` does not re-read `g_material`/`g_palette` when it builds `g_effect`, so a pre-create
material set is dropped for the initial frame. **The integrator must call `ApplyTheme()` right after
`CreatePanel()` and before the first `ShowPanel()`.** `ApplyTheme` is idempotent, allocation-free and
does no IPC, so calling it again is cheap. If P3.1's real `gt_panel_create` instead adopts a
previously-set palette/material (the `panel.h` comment "Before the first call P3.1 uses a built-in
dark default" hints it might), the explicit post-create call is still correct and harmless. Suggested
startup order: `CreatePanel()` → `ApplyTheme()` → `WatchAppearance(func(){ ApplyTheme() })`. `onChange`
runs on the main thread already and `ApplyTheme` is non-blocking, so it may call `ApplyTheme` directly
or bounce it onto the event loop — integrator's choice.

**Threading.** `ApplyTheme`, `WatchAppearance`, `StopWatchingAppearance` are main-thread-only (they
touch `NSApp` and the panel setters), same as every `panel.go` call — a goroutine caller wraps them in
`darwin.OnMain`. This differs from `observe.go`, whose C side owns its own thread; the theme KVO lives
on the main run loop, so there was nothing to gain from a private thread.

**Escalation — not a P3.4 change, but the integrator will hit it.** No `package main` importing
`internal/platform/darwin` links today: the P3.1 skeleton `panel.m` uses `CALayer` /
`kCAGravityResizeAspect` but no cgo file adds `-framework QuartzCore` to LDFLAGS (`shim.go` has
Foundation/AppKit/ApplicationServices/CoreGraphics only). `./scripts/check.sh` misses it because it
never links a binary (`go vet` + `go test`, and the mains have no test files). `cmd/gotab` fails the
same way. P3.1 or the integrator needs to add `-framework QuartzCore` to the package LDFLAGS. The
throwaway worked around it with its own LDFLAGS entry.

**Verification tool.** A throwaway `spike/themecheck/package main` drove the checks above (forced
appearance flips, watch/stop cycles, screenshot attempts). Deleted before commit, as required.
