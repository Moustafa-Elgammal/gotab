# P2.6 — Thumbnail capture with explicit C-side lifecycle

**Phase:** 2  **Depends on:** P1.7, P2.1  **Owns:** `capture.h`, `capture.m`, `capture.go`

## Goal

Capture a window thumbnail through ScreenCaptureKit and hand Go an opaque handle it must release.

## Files you may touch

- `internal/platform/darwin/capture.h`, `capture.m`, `capture.go` — **yours alone**
- `docs/tasks/P2.6.md` (tick acceptance, record findings)

**Do not touch** `shim.h`, `shim.m`, `shim.go`, `window.go`, `internal/app/`, `cmd/gotab/`,
`docs/ROADMAP.md`, `docs/DECISIONS.md`.

## Contract

`ImageRef` and `gt_image_release` already exist in `shim.go`/`shim.h` and are **frozen** — you produce
handles, you do not redefine how they are freed.

```go
// Capture grabs one window at up to maxWidth px. Blocking, time-bounded, and failable.
func Capture(id core.WindowID, maxWidth int) (ImageRef, error)
```

## Acceptance

- [x] a capture returns a live `ImageRef`; `Release()` frees it and `LiveImages()` returns to 0
  - A capture returns a live handle and `Release()` genuinely frees the bitmap: 14 held thumbnails
    moved the `IOSurface` row +2.3 MB against 2.1 MB declared and gave all of it back on release, and
    100 capture/release cycles left it at +0.0 MB.
  - **The counter is fixed.** P2.6 escalated it because `LiveImages()` returned to −1 — `g_images_live`
    in the frozen `shim.m` had a decrement (`gt_image_release`) and no increment. The integrator added
    `gt_image_adopt` to `shim.{h,m}` and `capture.m` now adopts at the line it had marked; `LiveImages()`
    reads 0 at rest, 1..5 as handles are taken, 0 after `Release`, and 0 after a double `Release`. See
    *Escalation* below and commit `fix: give gt_image_live a producer`.
- [x] a capture that does not answer times out and returns an error rather than hanging
- [x] thumbnails are **downscaled at capture time**, never captured full-res and shrunk
- [x] `./scripts/check.sh` green

## Findings

Measured on macOS 26.6.2, Apple silicon, 65-77 layer-0 windows on screen, via a throwaway
`package main` that was deleted before the commit (D16: no new tests).

**Cost, and it matches D12.** 193 ms cold, 57 ms warm, 56.7 ms mean over 100 cycles. D12's ~112/~46
was measured on a quieter machine; the shape is the same and the conclusion is unchanged — capture
stays off the summon path.

**Downscale happens at capture time and the number is exact.** One window, `maxWidth` swept:
64->64x42, 200->200x130, 400->400x263, 800->800x527, and 1200 and above all clamp to the window's
own 1046x689. `SCStreamConfiguration.width/height` yields precisely what is asked for, and `max_w`
is a bound rather than a target: a 64x64 window asked for at 100000 px stays 64x64 rather than
becoming a blurry bitmap.

**Release is clean, and the instrument was shown to be able to see it.** 100 cycles, sampled with
zero images held: `IOSurface` +0.0 MB from cycle 0 and from cycle 10. That zero is only worth
something with D14's control, so the run ends holding 14 thumbnails: +2.3 MB against 2.1 MB
declared, then -2.3 MB on release. The row moves when it should, so "no growth" means no growth.

**The timeout fires, is bounded, and leaves nothing behind.** Forced by temporarily building with a
1 ms bound *after warming the window cache*, so the capture phase is what times out rather than the
refresh: 40/40 returned `ErrTimeout`, the slowest call took 21 ms, and capture recovered completely
afterwards — 20/20 windows on the next pass, immediately and again after a settle. The 40 abandoned
completion handlers all fired later into a context nobody was waiting on; nothing crashed, no
libdispatch assertion, and `IOSurface` stayed at 0.0 MB, so the late handlers freed the images they
produced. That last part is why the capture context is heap-allocated and reference-counted instead
of `__block` on the stack: `spike/sck` deliberately leaked its result buffer on timeout and left a
note saying P2.6 could not.

**An ordinary capture failure rate that a caller has to expect.** Between 2 and 10 of 100 captures
failed with `ErrUnavailable` across runs, and retrying the failing id twice recovered none of them:
they are windows that CGWindowList reported and SCK will not capture, or that closed during the run.
This is why a capture failure maps to `ErrUnavailable` rather than `ErrInternal` — for a prefetcher
it is a normal event, and `ErrInternal` has to keep meaning "a bug in this shim" to stay actionable.
Callers should drop an id that keeps failing rather than retry it.

**Concurrency is safe but pointless.** Eight goroutines capturing at once, three rounds, 8/8 each
time — the C-side window cache behind its `pthread_mutex` holds up, and the capture itself runs with
the lock dropped. It buys nothing: D12 already measured SCScreenshotManager serialising in the
WindowServer, so a prefetcher should use one goroutine, not a pool.

**A stale cache entry never self-heals.** The shareable-window list is refreshed on a *miss* only, so
a window that closes while still in the cache fails every capture until something else forces a
refresh. Refreshing on failure instead would add ~46 ms to the common "the window really is gone"
case, so it is left as is — but it means a caller must not treat repeated failure as transient.

**assumption — the 2 s timeout is headroom, not a measured tail.** `captureTimeout` is 18x the cold
capture and 40x the warm one, chosen because capture never runs on the summon path so an over-long
wait costs one parked goroutine rather than a late panel. Nothing has yet observed the slow end of a
real capture distribution under load. Belongs against a V6 task.

**No `runtime.SetFinalizer` backstop, and the reason is structural.** `doc.go` expected the debug
leak detector to land with the first producer. It cannot: `Capture` returns `ImageRef` **by value**,
so there is no stable heap object to attach a finalizer to, and attaching one to a local before
copying it out would arm a finalizer that frees the bitmap while the caller's copy still points at
it — a use-after-free introduced by the leak detector. It needs `ImageRef` handed out as a pointer,
which changes a frozen type and the contract's signature. ARCHITECTURE.md is unaffected: the
finalizer was never the mechanism, only ever a detector.

## Escalation — the live counter has no producer side

`gt_image_live()` reports `shim.m`'s `static atomic_llong g_images_live`, and nothing increments it.
A handle produced by `gt_capture` is therefore never counted: `LiveImages()` reads 0 while an image
is held and -1 after it is released. The V6.4 leak assertion the counter exists for cannot be
written until this is fixed, and P2.6 owns neither `shim.h` nor `shim.m`. The minimal fix, for
whoever does own them:

```c
/* shim.h, beside gt_image_release */
// Takes an already-retained CGImageRef into the live count and returns it as a handle. The producer
// side of gt_image_release: without it the count only ever goes down.
gt_image_ref gt_image_adopt(void *retained_cgimage);

/* shim.m */
gt_image_ref gt_image_adopt(void *retained_cgimage) {
    if (!retained_cgimage) return NULL;
    atomic_fetch_add_explicit(&g_images_live, 1, memory_order_relaxed);
    return (gt_image_ref)retained_cgimage;
}
```

`capture.m` marks the single line where the call goes.

## Escalation — the weak link needs `scripts/build.sh`

`capture.go` carries both links behind a build tag, so nothing has to change for the gate:

```
#cgo !gotab_weak_sck LDFLAGS: -framework ScreenCaptureKit
#cgo gotab_weak_sck  LDFLAGS: -Wl,-weak_framework,ScreenCaptureKit
```

cgo evaluates the tag before it applies its LDFLAGS allowlist, so a plain `go build`/`go test`/
`go vet` links hard and needs no environment — measured, not assumed. Building the shipped binary
needs both the tag and the variable:

```
CGO_LDFLAGS_ALLOW='-Wl,-weak_framework.*' go build -tags gotab_weak_sck ...
```

Verified all three ways on this machine: default build links hard; the tag alone fails with
`invalid flag in #cgo LDFLAGS`; the tag plus the variable produces `otool -L` showing
`ScreenCaptureKit ... , weak)`. Until `scripts/build.sh` does this, `build/GoTab.app` will refuse to
launch on macOS 12.0-12.2 — dyld cannot find a framework that arrives in 12.3, and the process never
starts. It is a launch failure, not a missing feature.

## Notes

**Read `spike/sck/` first — it already solved this.** D12 and D14 are its findings: capture is ~46 ms
warm / ~112 ms cold, it does **not** parallelise, the completion handler fires on a Go-owned thread with
no run loop (so no AppKit marshalling is needed), output is IOSurface-backed, and `CGImageRelease` alone
is sufficient with no separate IOSurface step.

**D12: capture cannot happen on the summon path.** ~46 ms against a 100 ms budget. This API is for
capturing *ahead* of a summon; do not design it as something the summon path calls.

`spike/sck` notes ScreenCaptureKit is hard-linked because cgo rejects `-weak_framework` without
`CGO_LDFLAGS_ALLOW`. SCK arrives in macOS 12.3 and this project's floor is `minos 12.0` (D17), so a
hard link makes the binary refuse to load on 12.0–12.2. Weak-linking is the correct answer; if you need
`CGO_LDFLAGS_ALLOW`, **say so in your report** — `scripts/build.sh` is the integrator's file, not yours.
