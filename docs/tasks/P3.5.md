# P3.5 — Hotkey → loop

**Phase:** 3  **Depends on:** P0.2 (spike/hotkey), P2.7 (Loop.Post), P3.1–P3.4 + integration (D32)
**Owns:** `internal/platform/darwin/hotkey.{h,m,go}`, and the tap wiring in `cmd/gotab/main.go`

## Goal

Route the real ⌥⇥ chord into the event loop so `gotab -switch` is a switcher a person drives, not a
scripted demo. A session `CGEventTap` recognises the Option+Tab gesture, swallows the switcher's own
chord, and posts `Summon` / `Cycle` / `Activate` / `Dismiss` into `Loop.Post`.

## Contract

```go
type Gesture int // GestureSummonForward/Backward, GestureCycleForward/Backward, GestureActivate, GestureDismiss
func StartHotkey(fn func(Gesture)) error // ErrNotTrusted without the Accessibility grant
func StopHotkey()
```

The tap thread decides summon-vs-cycle (it tracks whether a Tab has been seen since Option went down),
so `fn` — and `cmd/gotab`'s `postGesture` — is a stateless switch. `fn` runs on the tap thread and
must not block; `Loop.Post` is non-blocking by construction (D22).

## Acceptance

- [x] a session tap at `kCGHeadInsertEventTap` recognises ⌥+Tab (forward), ⌥+⇧+Tab (backward),
      Option-release (commit), Esc (dismiss); autorepeat on a held Tab is ignored
- [x] the switcher's chord — ⌥+Tab keydown and its keyup — is swallowed; a modifier change and every
      other key pass through untouched
- [x] `kCGEventTapDisabledByTimeout` re-enables the tap
- [x] the tap runs on its own thread (like `observe.m`), so a keystroke is not queued behind a panel
      draw on the main run loop; the callback body is one `goHotkeyGesture(kind)` and nothing else
- [x] `StopHotkey` tears the thread down and does not return until it has, so `fn` cannot fire after;
      safe when not started and safe twice
- [x] without the Accessibility grant `StartHotkey` returns `ErrNotTrusted` and `gotab -switch` falls
      back to the scripted `demoDriver`
- [x] `./scripts/check.sh` green; `scripts/build.sh` produces the universal app

## Findings

- **Own thread, mirroring `observe.m`.** `gt_hotkey_start` detaches a `gotab.hotkey` thread that
  creates the tap, adds its run-loop source to its own loop, and runs `CFRunLoopRun()` until
  `gt_hotkey_stop` sets `g_stopping` and calls `CFRunLoopStop`. The alternative — adding the tap
  source to the main run loop `runloop.m` already runs — was rejected: a keystroke is the most
  latency-sensitive thing in the app and must not wait behind a CA commit or a `drawRect:`.
- **The gesture state (`g_armed`) lives on the tap thread, not in Go.** The first ⌥+Tab of a hold
  emits `SUMMON_*`; subsequent ones emit `CYCLE_*`; Option-release emits `ACTIVATE` only if armed.
  `cmd/gotab`'s `postGesture` then has no state — `SUMMON_FWD` becomes `Summon` + `Cycle(Forward)` so
  a single tap lands on the *next* window, which is the AltTab behaviour.
- **Autorepeat is dropped** (`kCGKeyboardEventAutorepeat`): a held Tab fires ~15×/s, too fast to
  cycle on, and a user who wants to spin can tap.
- **The Tab keyup is swallowed too** while armed, so the focused app never sees an orphaned keyup for
  a keydown it never got.
- **`Loop.Activate` raises now** (wired in D32): `postGesture` → `Activate` → `darwin.Raise(sel.ID)` →
  hide. So Option-release is a real switch.

### assumption → V6.1

Hotkey callback latency (event → `goHotkeyGesture`) is unmeasured — that is exactly what P0.2's
`spike/hotkey -manual -n 20` exists for, and it needs a human at the machine because a synthetic
event's timestamp is not on the HID path. The first C→Go crossing on the tap thread (the Go runtime
meeting a thread it has never seen) is likewise unmeasured and separated out there.

### Not verified here

The tap actually seeing and swallowing a real ⌥⇥, and the full summon→cycle→raise round trip, need
the Accessibility grant on the responsible process and a GUI session — the same wall P3.1's screenshot
and P0.2's measurement hit. `gotab -switch`'s no-grant path (fallback to `demoDriver`, clean SIGINT
exit) is smoke-tested; the granted path is V6.1/V6.5.
