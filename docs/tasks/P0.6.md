# P0.6 — ScreenCaptureKit capture prototype

**Branch:** feat/P0.6   **Phase:** 0   **Depends on:** none   **Blocks:** P2.6, and the whole Phase 2 capture design

## Goal

Prove a window thumbnail can be captured from Go, at a bounded size, and released. `CGWindowListCreateImage`
is obsoleted in macOS 15 (D3) — it is a compile error, not a warning — so the only path is
ScreenCaptureKit, which is **asynchronous and block-based**. From Go that means an Objective-C block
trampoline and a synchronous bridge, which is materially harder than the call it replaces. This is the
highest-risk unknown in the port; P2.6 is designed against whatever this finds.

## Files you may touch

## What has to be answered

1. Does SCK deliver its completion handler when called from a Go-owned thread that is **not** running an
   NSRunLoop? If it needs a run loop, every capture has to be marshalled to the AppKit thread, and that
   changes Phase 2's threading design.
2. What does a capture cost, cold and warm? The summon budget is < 100 ms for the whole path.
3. Does the returned `CGImageRef` release cleanly — does `CG raster data` return to baseline?
4. Can the bitmap be **downscaled at capture time** (memory rule #4) rather than captured full-res?

## Acceptance

- [x] A thumbnail of a real window is captured from Go and its dimensions reported — 400x237 from a
      1512x897 window, and full-res when asked
- [x] Capture latency measured, cold and warm — 112 ms cold, 46 ms warm, plus 46 ms to enumerate
- [x] Backing store measured while held and after release — **not** `CG raster data`: SCK output is
      IOSurface-backed and invisible to `spike/procmem`'s rows. 330.5 MB held -> 64 K released, read from
      `vmmap --summary`'s `IOSurface` line
- [x] Findings appended to `docs/DECISIONS.md` (D12) — **SCK does not need a run loop**; the completion
      handler fires on a Go-owned thread

## What it actually found

The task asked four questions and all four came back benign. The two it did not ask are the ones that
changed the design, both in D12:

- **Capture does not parallelise.** ~46 ms is fixed WindowServer round-trip, identical for a 400 px
  thumbnail and a full-res one; 10 concurrent captures cost 324 ms against 460 ms serial. A 100 ms summon
  cannot contain even one capture plus an enumeration, so **thumbnails must be captured before summon.**
  That is a constraint on P2.6 and P3.1, not on this spike.
- **CoreGraphics aborts a non-AppKit process** on its first capture — `CGS_REQUIRE_INIT`, an `abort()`
  with nothing to catch — unless a CG display call has run first. `sck_init` is `CGMainDisplayID()` for
  that reason and is not optional. P0.1 and P0.2 will meet the same thing.

## Notes

Weak-link the framework (`-weak_framework ScreenCaptureKit`), as AltTab does, so the binary still loads on
a system without it. **Put a timeout on the synchronous bridge.** A spike that hangs forever teaches
nothing; one that reports "the completion handler never fired" teaches the most important thing here.
