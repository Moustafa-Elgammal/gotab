# P4.1 — Preferences

**Phase:** 4  **Depends on:** P3.1–P3.5 (the settings have consumers)
**Owns:** `internal/prefs/`, `internal/platform/darwin/prefs.{h,m,go}`, the `SetAppearance` override in
`theme.go`, and the `-prefs` command + prefs wiring in `cmd/gotab/main.go`

## Goal

Persist the switcher's settings in the standard macOS preferences plist for the bundle id
(`app.gotab`), read them at startup, and expose them for editing before the settings UI (P4.2) exists.
`defaults read app.gotab` / `defaults write app.gotab` address the same store.

## Contract

- `internal/prefs` (pure Go) — `Prefs` struct, `Default()`, `Load(Reader) Prefs`, `(Prefs) Save(Writer)`,
  `(Prefs) Set("Key=Value")`, and the derivations `LayoutOpts()` / `Rules()`. Keys are the exported
  field names; a missing or mistyped key falls back to `Default()`, never Go's zero.
- `internal/platform/darwin.Prefs` implements `prefs.Reader` + `prefs.Writer` over
  `CFPreferencesCopyAppValue` / `CFPreferencesSetAppValue` (`prefs.{h,m,go}`).
- `gotab -prefs` prints the effective settings; `gotab -prefs Key=Value …` applies, saves, and prints.
- `gotab -switch` reads prefs at startup for the tile layout, the thumbnail cache bound, and the
  appearance.

## Acceptance

- [x] a `Prefs` round-trips through the CFPreferences domain: `-prefs Key=Value` then `-prefs` shows
      the change; a fresh domain reports `Default()`
- [x] from the built `.app` the domain is `app.gotab` and `defaults read app.gotab` shows the same
      keys/values — verified: `MaxColumns = 3`, `HotkeyModifiers = 524288`, `BlockedApps = ()` after
      `gotab -prefs MaxColumns=3`
- [x] `-switch` uses `MaxColumns` / `TileWidth` / `TileHeight` (via `core.LayoutOpts`),
      `ThumbnailCacheSize` (the prefetcher bound), and `Appearance` (forced Light/Dark, or follow)
- [x] an unknown key or unparseable value is rejected and nothing is written
- [x] `./scripts/check.sh` green; `scripts/build.sh` produces the universal app

## Findings

- **The domain is the running binary's identity, not a hard-coded string.** From `build/GoTab.app` it
  is `CFBundleIdentifier` = `app.gotab` and interops with `defaults`. Under `go run` / a bare `go
  build` binary it is that binary's name (`~/Library/Preferences/<name>.plist`), so a dev build's
  settings land in their own throwaway domain — the same identity rule TCC uses, and the honest
  behaviour: a dev build must not scribble on the real prefs. Stated in `prefs.h`.
- **String arrays cross cgo as `'\n'`-joined text** (`BlockedApps`). A window-server application name
  never contains a newline; a stored element that did would be split wrongly. Noted in `prefs.h`.
- **`Save` writes the whole record, not a diff.** A field left at its default is still persisted, so a
  later change to `Default()` does not silently move a user's setting out from under them.
- **`Appearance` override lives in `theme.go`** as an `atomic.Int32` that `ApplyTheme` consults; under
  a forced Light/Dark the `WatchAppearance` callback's re-apply becomes a no-op that ignores the
  system flip. No `theme.m` change.

### Schema-only for now — wired by a later Phase 4 task, not this one

- **`ShowMinimized` / `ShowHidden` / `ShowOtherSpace` / `ActiveAppOnly` / `BlockedApps`.** The filter
  kernel `core.Filter` (P1.3) exists and `Prefs.Rules()` builds a `core.Rules`, but **the event loop
  never filters** — `internal/app/loop.go`'s `doRescan` orders every window. Wiring `core.Rules` into
  the loop (a `Loop.Rules` field applied before `Order.Rebuild`, and a `core.Order` that rebuilds from
  a filtered row set) is its own change. It belongs with **P4.4** (multi-monitor & Spaces also touch
  the filter) or a task of its own. `assumption` → until then these prefs are inert.
- **`HotkeyKeyCode` / `HotkeyModifiers`.** In the schema and `Default()` (48 / `0x80000` = ⌥Tab), but
  `hotkey.m`'s tap still matches a fixed keycode. Making `gt_hotkey_start` take a chord is small;
  it is left to **P4.2** (rebinding is a settings-UI feature) or a follow-up. `assumption` → the
  hotkey is not yet rebindable.

### assumption → V6.8

`panelRenderer` still hard-codes `Scale: 2` after `LayoutOpts()` — Retina assumed. A task that reads
the actual display's backing scale (P4.4) removes it; V6.8's alloc/scale pass is where it is checked.
