# P4.2 — Settings UI

**Phase:** 4  **Depends on:** P4.1 (the schema and the store), P3.5 (the hotkey)
**Owns:** `internal/platform/darwin/settings.{h,m,go}`, the configurable-chord change in
`hotkey.{h,m,go}`, `HotkeyDisplay` in `hotkey.go`, and `-settings` + `runSettings` in `cmd/gotab`

## Goal

A native window to edit the switcher's settings, over the same CFPreferences domain the `-prefs` CLI
and `defaults(1)` use. Every control writes through `prefs.Set` and persists immediately — no Apply
button.

## Contract

- `gt_settings_open` builds one fixed-size `NSWindow` with a control per setting; each change becomes
  `goSettingsAssign("Key=Value")`. `gt_settings_set_*` seed the controls; `goSettingsClosed` fires on
  the red button.
- `darwin.OpenSettings(SettingsValues, func(kv string))` / `SettingsSetHotkey` / `CloseSettings` /
  `OnSettingsClosed` — `SettingsValues` is primitives only, so `darwin` does not import
  `internal/prefs` (it never has — `darwin.Prefs` implements `prefs.Reader/Writer` structurally).
- `gt_hotkey_start(keycode, modifiers)` — the chord is no longer fixed. `modifiers` shares its bit
  values with `NSEvent`'s device-independent flags, so the recorder passes its mask straight through.
- `gotab -settings` opens the window on its own run loop; `-switch` reads `HotkeyKeyCode` /
  `HotkeyModifiers` from prefs.

## Acceptance

- [x] the window builds with a control for every wired setting — 4 filter checkboxes, a blocked-apps
      text field, an Appearance popup, Columns and Thumbnail-cache steppers, and a hotkey recorder —
      seeded from the loaded prefs; `gotab -settings` runs the loop and exits 0 on close / ^C
- [x] a control change is one `Key=Value` that `prefs.Set` parses and `Save` persists to the
      `app.gotab` domain — the same path `-prefs Key=Value` exercises, verified there
- [x] the hotkey chord is configurable end to end: `-prefs HotkeyKeyCode=49 HotkeyModifiers=…` is read
      by `-switch`'s `StartHotkey`; `HotkeyModifiers=0` is rejected (a bare key would be swallowed
      session-wide), and `StartHotkey` guards it again at use
- [x] `Shift` beyond the chord's own modifiers still means "cycle backwards"; `Esc` still dismisses
- [x] `./scripts/check.sh` green; `scripts/build.sh` produces the universal app

## Findings

- **`-settings` is its own process.** It shares nothing with a running `gotab -switch` — it writes the
  plist, and `-switch` picks changes up on its next launch. Live application into a running switcher
  needs IPC or a shared process and is a later concern; the window says nothing misleading about it.
- **The app goes `NSApplicationActivationPolicyRegular` while the settings window is open** (it is
  `Accessory` for the panel). A settings window that could not take focus or show in the Dock would be
  wrong; `-settings` never creates the panel, so there is no conflict.
- **One assign form, one callback.** Every control funnels through `emit(key, value)` → `"Key=Value"`
  → `prefs.Set`. Reusing P4.1's parser meant no per-control marshalling and no second schema. The
  recorder sends `HotkeyKeyCode=` then `HotkeyModifiers=`; `runSettings` refreshes the button label
  once, after the second.
- **`hotkey.m` generalised cleanly.** `g_chord_key` / `g_chord_mods` replace the hardcoded Tab +
  Alternate; the "modifiers released → commit" edge is now `g_chord_was_held` transitioning, which
  works for any modifier set. If a chord includes Shift, backward-cycle is unavailable (Shift can't
  mean two things) — an acceptable corner.
- **`HotkeyDisplay` is the only chord formatter.** The recorder does not format its own label in C; it
  emits the raw values and Go's `HotkeyDisplay` (a small keycode table plus the four modifier
  symbols) produces the string, so there is one place it is done. Uncommon keycodes show as a number.

### Not in the window, by choice

`TileWidth` / `TileHeight` are in the schema and the `-prefs` CLI but not the window — `0 = auto` does
not read well as a stepper, and they are niche. `ActiveApp` and `CurrentSpace` are runtime, not
settings. The filter checkboxes **write** but the event loop still does not **read** `core.Rules`
(P4.1's open item) — wiring that is P4.4's or its own.
