# V6.3 — summon → pixels, end to end

**Phase:** 6   **Needs:** a real Mac with a window server (an agent/CI host has none). No human
interaction beyond launching it.
**Discharges:** the Phase 0 target "summon → pixels on screen < 100 ms", which was budget-allocated
(drawing 1.3 ms D13, capture ~46 ms and unparallelisable D12, enumeration 0.30 ms warm D5) but
never timed end to end on the assembled app.

## Goal

Measure the wall-clock from "summon gesture recognised" to "the panel's first frame is on screen",
against the **< 100 ms** budget. Timed to the **CA commit**, not to the call returning — D13 showed
`orderFrontRegardless` returns in ~1 ms while the cold frame does not commit for ~14 ms, so timing
the call is wrong by 10x.

## Prerequisites

- `build/GoTab.app`, Accessibility granted (Screen Recording optional — thumbnails are prefetched
  off the summon path by design, D12, so their absence must not change the number).
- Instrumentation: add a timestamp at gesture recognition (`hotkey.m`'s gesture post) and one in a
  `CATransaction` completion handler on the panel's first show (`panel.m`), printed to stderr. This
  is V6.3's own scaffold — keep it behind a build tag or a `-timing` flag, do not ship it.

## Protocol

1. Launch the bundle. Let it settle (the first enumeration's cold cost is paid at launch, D5 — it is
   not part of a summon).
2. Summon 30 times with the panel fully dismissed between each. Record gesture→commit for each.
3. Report cold (first summon after launch) separately from warm (the rest), min / median / p95 /
   max.

## Acceptance

- [ ] Warm p95 gesture → CA-commit **< 100 ms**.
- [ ] Cold summon reported separately; if it is over budget, that is a launch-warmup question (D5),
      not necessarily a fail — record it and decide.
- [ ] The number holds with Screen Recording **off** (proves capture is genuinely off the summon
      path).
- [ ] Numbers appended to `docs/DECISIONS.md`; `docs/ROADMAP.md` Phase 0 target table and Phase 6
      row updated with the measured figure.

## If warm p95 is over 100 ms

The budget breakdown (D12/D13/D5) says the spend is on data. Look first at whether `doRescan` is
running on the summon path (it must not — enumeration is event-driven, the summon only reconciles
selection and lays out), then at `panelRenderer.onState` doing work it could have done ahead of time.
Send the finding back to the phase that owns the cost.
