# P0.4a — Build a trustworthy memory instrument

**Branch:** feat/P0.4a   **Phase:** 0   **Depends on:** none   **Blocks:** P0.4b, and every memory claim

## Goal

A command that reports the *real* memory held by CoreGraphics bitmaps in our own process. Right now we
have no such thing: `spike/memory` allocates 366 MB of CGImages and `task_info(TASK_VM_INFO)` reports
about 8 MB of growth (see `docs/DECISIONS.md` D4). Until this is fixed, no statement about this project's
memory — including "it beats a comparable switcher" — means anything.

## Files you may touch

- `spike/memory/main.go` (add reporting; do not change what it allocates)
- `internal/memprobe/` (new package, if the instrument is worth keeping)
- `docs/DECISIONS.md` (append findings)

Nothing else. Do not start Phase 1.

## Approach — try in this order, stop when one works

1. **`vmmap --summary <pid>`** — parse the region breakdown. CoreGraphics backing store usually appears
   under `CG image`, `IOKit`, or `MALLOC_LARGE`. Cheapest to try.
2. **`footprint -p <pid>`** — Apple's own accounting tool; may attribute purgeable memory the task_info
   path omits.
3. **`CGImageGetDataProvider` + `CGDataProviderCopyData`** — force materialisation of the backing store,
   then measure. This distinguishes "not counted" from "not allocated", which D4 leaves open and which
   changes what the fix is.
4. Instruments allocations template, if the above are inconclusive.

Hypothesis worth testing first: CoreGraphics defers materialising the bitmap until the image is actually
drawn or read. If so the memory was never allocated, and the finding is *"our thumbnail cache costs less
than expected until first draw"* — which changes the caching design, not just the instrument.

## Acceptance

- [ ] Running the instrument against `spike/memory` while it holds 200 images reports **≥ 300 MB**
      (arithmetic says 366 MB; anything in that region proves we can see it)
- [ ] The same instrument reports the drop after `releaseAll()`
- [ ] `docs/DECISIONS.md` gains an entry stating which mechanism worked and what the true numbers are
- [ ] `docs/ROADMAP.md` P0.4a is `[x]` in the same commit

## Notes

If it turns out the memory genuinely is never allocated until draw, say so plainly and mark P0.4 resolved
with that explanation rather than inventing a way to make the number appear. A negative result that is
*correct* is the goal here; the point of Phase 0 is to find these out cheaply.
