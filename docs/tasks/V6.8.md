# V6.8 — no allocation on the hot path, after Phases 2–5 wired real data through

**Branch:** verify/hot-path-allocs   **Phase:** 6   **Depends on:** P1.1–P1.7 (the 0-alloc kernels),
P3.1 / D32 (the `panelRenderer` bridge), P4.4 (the loop filters every rescan).

## Goal

docs/ARCHITECTURE.md: summon, keystroke-while-cycling and dismissal are latency-critical and must
allocate nothing. Phase 1 proved that per kernel with `-benchmem`. This task re-checks it now that
the loop drives those kernels with **real enumerated windows, a live filter and a rebuilt order every
pass**, and settles the one `assumption` the roadmap tagged at V6.8: `panelRenderer.onState` builds
two fresh slices per state change.

## Notes — the `panelRenderer.onState` allocation

`cmd/gotab`'s `panelRenderer.onState` runs on the loop goroutine after every state change and does:

```go
tiles := make([]darwin.Tile, n)       // 80 B/elem
reqs  := make([]darwin.ThumbRequest, n) // 32 B/elem
```

Two heap allocations, `n * 112` bytes total: **784 B at 7 windows, 2240 B at 20**. Measured via
`unsafe.Sizeof` on the two structs.

**Accepted, not fixed.** The reason the slices are fresh each call is real: they are handed to an
async `darwin.OnMain` closure and to `pf.Want`, and the loop goroutine would overwrite a reused
backing array before the main thread read it. Removing the allocation needs a `sync.Pool` with the
closure returning the buffer, or an N-deep ring — lifecycle complexity that is not worth it here
because:

- it is **not** on a `core` hot path — `core.Layout` stays 0-alloc, and this is the bridge above it;
- it is **bounded** by the switchable window count (tens), not by anything unbounded;
- it fires **once per gesture** (a summon, or one cycle keystroke), not once per frame or per
  prefetched thumbnail;
- 2 KB on a keystroke that already crosses into AppKit is below the noise floor of the ~46 ms capture
  and ~1.3 ms draw the summon budget is actually spent on (D12, D13).

If a future CPU profile of a real session ever shows this mattering, the fix is to lift the
tile/request build into a `panelRenderer` method and give it a pooled buffer — noted here so the
option is on record. The roadmap `assumption` tag at Phase 3 is discharged by this note.
