## Goal

The one goroutine that owns mutable state. `ARCHITECTURE.md` has had `internal/app` in its diagram since
the beginning and the roadmap never had a task for it; P2.3b surfaced the omission, because "callbacks
enqueue only" needs somewhere to enqueue **to**.

## What has to be answered

1. **What may a platform callback do?** `ARCHITECTURE.md#the-cgo-rule` says enqueue and return: no
   allocation, no logic, no logging. A channel send that can block is none of those things — an event
   tap whose callback stalls is disabled by the system (`kCGEventTapDisabledByTimeout`, P0.2's notes).
   So posting must never block, and what happens when the queue is full has to be a decision.
2. **What is allowed to reorder the list?** PLATFORM-LESSONS §3: an attention decision or a structural
   repair, never a title change. Re-enumeration touches every window and must not disturb MRU order.
3. **Does the model survive windows vanishing underneath it**, given removal is swap-with-last?

## Acceptance

- [x] one goroutine owns `Model`, `Order` and `Selection`; no mutex anywhere in the package
- [x] posting an event never blocks, from any thread — non-blocking select with a `default`, two
      mechanisms because a full queue means different things for a keystroke and for "something
      changed" (D22)
- [x] a re-enumeration that changes no titles and no membership leaves MRU order untouched — 12
      rescans, 1 state print. The title-change case specifically was **not** observed here; it is
      pinned in core by `TestModelUpsertZeroFocusPreserves`
- [x] windows that vanish are removed; selection survives it via `Selection.Reconcile`. The backwards
      delete is safe because removal is swap-with-last — pinned by `TestModelRemoveMiddleFixesMovedRow`
- [x] `./scripts/check.sh` green

Per D16 this task writes no tests.
